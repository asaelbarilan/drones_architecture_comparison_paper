# What makes an LLM/VLM drone architecture work: the "handles" (D-167, 2026-10-22)

**NO CODE CHANGED.** Research note. PDFs: `papers/handles/` (README there).

## Question

Our paper matrix (D-166) runs the textbook architectures (C0-C13) on one model and one runtime.
Seed 1060: every model-driven architecture solves the basic tasks but none of the four planning
tasks (conditional gate, ordered visit, closing passage, follow).

The user's observation: the systems that work (drone_control, AerialClaw) do so because of logic
that lives outside the architecture diagram:
- the prompt logic;
- the task contracts;
- the state hand-offs;
- the flow between parts.

The question: what does the field say these "handles" are, and how much do they matter?

## Vocabulary

The field calls this the **scaffold** or **harness** around the model: the interfaces, state
tracking, verification and feedback loop. AgentSpec 2026 uses "scaffold"; the UAV MCP DroneServer
2026 uses "agentic harness". LLM-Modulo calls the checking part "external critics / verifiers".
Inner Monologue calls the feedback part "closed-loop language feedback" / "success detection".

## Evidence from the literature

| Work | Finding relevant to the thesis | Link |
|---|---|---|
| LLM-Modulo (Kambhampati et al., ICML 2024) | Autoregressive LLMs cannot plan or self-verify by themselves; they work as approximate knowledge sources inside a loop with external model-based critics/verifiers | [2402.01817](https://arxiv.org/abs/2402.01817) |
| AgentSpec (Chen et al., 2026) | "Agent performance is governed by scaffold compatibility and interaction effects rather than isolated module strength"; "composition can outweigh model scale"; memory helps only when its representation matches the reasoner. DeliveryBench, same model: ReAct 18.57 -> 34.70 with a memory bank | [2606.14674](https://arxiv.org/abs/2606.14674) |
| Embodied Agent Interface (Li et al., NeurIPS 2024) | Breaks LLM embodied decision-making into goal interpretation, subgoal decomposition, action sequencing and transition modelling. Most failures are module-level (hallucinated objects, unmet preconditions, missing / misordered steps), invisible in success rate alone | [2410.07166](https://arxiv.org/abs/2410.07166) |
| Inner Monologue (Huang et al., CoRL 2022) | Feeding success detection and scene description back into the planner prompt is what lets an LLM planner retry, replan and finish long instructions; open-loop plans could not | [2207.05608](https://arxiv.org/abs/2207.05608) |
| ProgPrompt (Singh et al., 2022) | Program-like prompts: action APIs, example programs, natural-language comments and precondition assertions with recovery. Comments and assertions measurably raise success / executability | [2209.11302](https://arxiv.org/abs/2209.11302) |
| SayCan (Ahn et al., 2022) | The LLM's choice is multiplied by a learned affordance (can this skill succeed here?); the language model alone proposes infeasible steps | [2204.01691](https://arxiv.org/abs/2204.01691) |
| Code as Policies (Liang et al., 2022) | Success depends on the API (perception and control primitives) and the few-shot examples handed to the model | [2209.07753](https://arxiv.org/abs/2209.07753) |
| TypeFly (Chen et al., 2023) | Drone LLM planning through a small DSL (MiniSpec) plus a "query" skill and replanning; ablations show these design choices, not the LLM alone, decide complex-task success and halve cost / latency | [2312.14950](https://arxiv.org/abs/2312.14950) |
| CoPAL (2023); Garrabé et al. (2024) | Mid-execution failures need multi-level corrective feedback. Missing / mischaracterised subgoals are a main failure mode; an "expected outcomes" module plus feedback recovers them, especially with small local models | [2310.07263](https://arxiv.org/abs/2310.07263), [2411.05474](https://arxiv.org/abs/2411.05474) |
| Bode et al. (2024) | Prompt-engineering technique and combination change service-robot task completion; prompts released | [2410.22997](https://arxiv.org/abs/2410.22997) |
| DroneServer / MCP harness (Ramos Silva & Burke, 2026) | 98 typed drone tools, server-side mission state, tiered validation, independent geofence: 8 of 11 LLMs completed 90-100 % of the simulated missions; no geofence escape in 110 trials. Reliability across models comes from the harness (no harness-off ablation reported) | [2601.15486](https://arxiv.org/abs/2601.15486) |
| AerialClaw (Li et al., 2026) | A brain-skill-runtime loop: SOUL / BODY documents (identity and capability bounds), soft-skill strategy notes, a validated one-skill-per-turn JSON decision, explicit done / stuck verdicts, execution feedback, memory, reflection | [2606.12142](https://arxiv.org/abs/2606.12142) |
| Our earlier 94-paper UAV survey (drone_control, `survey_llm_planning_uavs_systematic`, Table 8) | Typed tools help, "but every tool call needs preconditions, state grounding, and safety authorization". The main gap is semantic-to-metric grounding. Benchmarks rarely compare architectures under identical constraints | local |

**What the field tried and dropped:** the "LLM writes the whole plan once" (open-loop) design.
Inner Monologue and CoPAL replaced it with closed loops. SayCan and LLM-Modulo replaced "trust
the LLM's step" with a feasibility or critic check. Free-form text plans were replaced by typed
APIs or DSLs (ProgPrompt, Code as Policies, TypeFly).

## Evidence from our own repositories (checked against the code)

**drone_control** (`src/agent/`). The working loop is a set of handles around the models:

| Handle | Where | What it does |
|---|---|---|
| Pinned reasoning order + task-policy library | `task_policies.py` | The VLM prompt fixes the order *mission -> required evidence -> current evidence -> gap -> action*; one task policy is picked once per mission. Written after run 20260812_134500, where all 14 VLM reasons cited detections and none cited coverage |
| Capability allow-list | `capability_registry.py` | A deterministic allow-list given to the LLM mission compiler |
| Typed mission contract | `mission_compiler.py` (PlannerAdapter), `contracts.py` | The LLM response is converted into a typed contract; invalid messages raise |
| Proposal gate | `proposal_gate.py` | First deterministic gate on model proposals (mission / subgoal context) |
| Single sequencing owner | `mission_executive.py` | "Single owner of reactive mission sequencing" |
| Fused, freshness-limited world snapshot | `blackboard.py` | Async perception fused into one timestamped snapshot with freshness limits; only a "mature" track counts as found |
| Decision FSM | `decision_manager.py`, `skill_state_machine.py` | World state -> pilot skill |
| Progress monitor | `progress_monitor.py` | Low-rate, OnFly-inspired |

Its recent fixes are handle fixes, not model fixes:
- S10: a routine VLM answer no longer releases a candidate mid-inspection.
- B12: the close-range check turns thinking off.
- S9: the crowd gate uses the standard LOF threshold.

**AerialClaw in our testbed (C1, D-44 / D-105).** It is the one paper family that passed its
gate (5/5 grid, 5/5 object search). The handles it had:
- SOUL/BODY documents;
- soft-skill strategy;
- runtime precondition checks;
- explicit done / stuck verdicts;
- per-turn feedback;
- perception rendered as labelled metric detections.

D-85 already noted that the labelled detections gave C1 a perception input the VLM families did
not have.

**The live shared-Qwen stack, same weights, no training.**

| Period | Result | What changed (handles only) |
|---|---|---|
| D-143 -> D-145 | 0/4 -> 4/4 numeric tasks | monitor status semantics, numeric completion contract, ordered-step preservation |
| D-150 -> D-158 | 0/9 -> 5/9 capability tasks | world-pose contract, standoff fix, altitude hold, object memory, standoff / hold read from step text, monitor "hold" with fresh near depth counts as stop |

**The D-166 matrix.** The vanilla C configurations, which have only the diagram's modules, pass
basic tasks and fail every planning task. The ordering among them (C5/C6 above C2-C4) comes from
the components that act as handles: memory and recovery.

## Taxonomy for the paper (handles as experimental factors)

| ID | Handle | Literature | Our evidence | Target tasks |
|---|---|---|---|---|
| H1 | Typed task contract with branch / sequence semantics (conditions, ordered steps, completion evidence per step) | ProgPrompt, TypeFly, EAI subgoal errors | D-144/145 ordered steps; conditional_gate "branch flattened" | conditional_gate, ordered_visit |
| H2 | Single sequencing owner / executive with explicit step state | drone_control MissionExecutive, AerialClaw runtime | D-145, D-158 | ordered_visit, closing_passage |
| H3 | Pinned reasoning order + task-policy library in prompts | drone_control task_policies, Bode 2024 | run 20260812 | search / perception tasks |
| H4 | Evidence-based completion (success detection) | Inner Monologue, CoPAL | D-147/148/158 stop rules | approach_hover, overturned_vehicle |
| H5 | Perception -> semantic state hand-off (labelled, metric, fresh) | Code as Policies API, Blackboard | C1 labelled detections (D-85), D-147 grounding | all visual |
| H6 | Feasibility / precondition critics before execution | SayCan, LLM-Modulo, DroneServer | verifier C3, SUPER (D-165) | obstacles, gate |
| H7 | Feedback of outcomes into the next prompt + bounded memory | Inner Monologue, AgentSpec memory | C5 / C6, skill history in C1 | closing_passage, follow |
| H8 | Recovery invocation policy (when to call the reasoner) | PMR, OnFly | C6 vs C10 vs C13 | closing_passage |

## Implication and proposed next experiment (not started)

The paper's first finding: **vanilla architectures do not work by themselves; the handles do.**
To measure this rather than assert it:
1. Keep the D-166 vanilla matrix as the "diagram only" condition.
2. Build the handles H1-H8 as switchable components on the same runtime (several already exist
   in the live stack).
3. Run add-one (vanilla + Hk) and remove-one (full - Hk) ablations on the same tasks and seeds.

The prediction from the literature and our history: the handles explain more variance than the
choice among C configurations.

## Out of scope

- Training a bigger model or new VLA weights: the thesis is about the scaffold at fixed weights.
- Cloud models: one local model is a paper rule (D-159).
- Task-specific scripted behaviours that read evaluator truth: never allowed (AGENTS.md rules).
  Handles must use public mission text and sensed state only.
